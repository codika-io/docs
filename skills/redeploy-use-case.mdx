---
title: "redeploy-use-case"
description: "Skill for redeploying an existing process instance with updated parameters without creating a new template version"
---

## When to use

- Change deployment parameters on a running instance (e.g., company name, language, timezone)
- Retry a failed deployment without redeploying the entire use case
- Apply configuration changes after publishing without creating a new version

## Prerequisites

- `codika` CLI installed and authenticated
- An existing deployment with `project.json` containing `devProcessInstanceId` or `prodProcessInstanceId`
- API key with `deploy:use-case` scope

## Command

```bash
codika redeploy [options]
```

## Options

| Option | Description | Default |
|--------|-------------|---------|
| `--process-instance-id <id>` | Target process instance ID | — |
| `--path <path>` | Path to use case folder with `project.json` | Current directory |
| `--project-file <path>` | Custom project file path | `project.json` |
| `--environment <env>` | Target environment (`dev` or `prod`) | `dev` |
| `--param <KEY=VALUE>` | Set a single parameter (repeatable) | — |
| `--params <json>` | JSON string with parameters | — |
| `--params-file <path>` | Path to JSON file with parameters | — |
| `--force` | Force redeploy on non-failed instances | `false` |
| `--json` | JSON output | — |
| `--api-key <key>` | Override API key | — |
| `--api-url <url>` | Override API URL | — |

## Parameter merge behavior

<Info>
**Parameters are merged, not replaced.** You only need to pass the parameters you want to change. The platform merges them with the instance's existing parameters — omitted parameters keep their current values.
</Info>

Three input methods, merged with this priority (highest wins):

1. `--param KEY=VALUE` flags (repeatable)
2. `--params '{"key": "value"}'` JSON string
3. `--params-file ./params.json` JSON file

## What happens on redeploy

1. Resolve process instance: `--process-instance-id` > `project.json` (dev/prod based on `--environment`)
2. Load the current deployment template from the platform
3. Merge provided parameters with existing instance parameters
4. Re-run placeholder replacement with updated parameters
5. Deploy updated workflows to n8n using the instance owner's credentials
6. Return success with parameter change summary

No new template version is created. The instance continues running the same template with updated runtime parameters.

## Agent usage

When automating redeploy, prefer `--params` with JSON and `--json` for structured output:

```bash
codika redeploy --params '{"COMPANY_NAME":"New Corp","LANGUAGE":"fr"}' --json
```

This avoids shell escaping issues with `--param` and provides machine-readable output.

## Examples

```bash
# Change a single parameter on dev
codika redeploy --param COMPANY_NAME="New Corp"

# Multiple parameters
codika redeploy \
  --param COMPANY_NAME="New Corp" \
  --param LANGUAGE=fr

# JSON parameters (agent-friendly)
codika redeploy --params '{"COMPANY_NAME":"New Corp","LANGUAGE":"fr"}' --json

# From file
codika redeploy --params-file ./updated-params.json

# Retry a failed deployment (no --force needed)
codika redeploy --environment dev

# Redeploy prod instance with updated params
codika redeploy --environment prod --param LANGUAGE=fr --force

# Custom project file
codika redeploy --project-file project-client-a.json --param LANGUAGE=fr
```

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Redeploy successful |
| `1` | API error or deployment failure |
